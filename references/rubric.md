# 评分标准

## 一、门槛项（任一不过 → 建议退回补充）

| # | 门槛 | 不过的样子 |
|---|---|---|
| G1 | 说得出为什么做 | 全文找不到一个具体的麻烦/问题，只有"提升效率""优化体验" |
| G2 | 有明确的使用者 | 说不出谁会用、谁会看 |
| G3 | 有业务负责人/决策人 | 不知道该找谁确认 |
| G4 | 涉及客户数据、跨境数据、销售话术、产品要素时，提到了合规 | 涉及但只字未提（不涉及则视为通过） |

## 二、四维评分（满分 100）

### D1 痛点与背景（35 分）

看三件事：问题交代清楚了没有、有没有证据、因果链合不合理（因为 X → 导致 Y 麻烦 → 所以要做 Z）。

| 分档 | 样子 |
|---|---|
| 30–35 | 讲清楚遇到什么麻烦、多频繁、影响谁、损失了什么；有数据或具体案例；因果链完整，读完就知道为什么非做不可 |
| 20–29 | 问题讲到了，有部分数据或案例；但"损失了什么"或"卡在哪一步"不清楚 |
| 10–19 | 问题是从系统角度描述的（"缺乏结构化字段""无法检索""未线上化"），没讲业务上吃了什么亏；或有数据但和问题脱节 |
| 0–9 | 只有口号式目标，或通篇背景铺垫没有问题 |

常见扣分：
- "缺少 X 功能"当痛点（这是方案，不是痛点）
- 有总量数据（进来 N 个、成交 M 个）但没说在哪一环流失
- "容易出现…"类推测，没有一个实例

### D2 用户场景四要素（30 分）

四要素各 7.5 分：**谁**、**在什么场景**、**遇到什么事**、**希望怎么样**。

| 要素 | 满分的样子 | 扣分的样子 |
|---|---|---|
| 谁 | 具体角色、人数/规模、有几类使用者（录入的人、看结果的人） | 只写"用户""一线人员""相关人员" |
| 场景 | 在什么环节、什么时机、用什么工具 | 没有场景，只有功能列表 |
| 遇到什么事 | 具体事件或案例（某个客户、某次跟进） | 抽象概括 |
| 希望怎么样 | 期望的结果/状态（"跟进不再漏""一眼看到卡在哪"） | 只写希望加什么功能，没说要达到什么效果 |

有一个以上真实案例（哪怕是脱敏的对话、截图描述）在"遇到什么事"上直接拿满。

### D3 痛点和诉求对得上（10 分）

把文档里提的每个诉求/功能块，对回前面的痛点。

| 分档 | 样子 |
|---|---|
| 9–10 | 每个诉求都能对回某个痛点 |
| 5–8 | 大部分对得上，有一两块诉求找不到对应痛点 |
| 0–4 | 痛点讲 A，诉求做 B；或大块诉求（尤其占篇幅的）没有痛点支撑 |

另外看是否给了优先级和时间预期；完全没有扣 2 分。

### D4 精简度（25 分）

有效内容占比 = （痛点 + 场景 + 业务规则 + 业务期望）字数 / 全文字数。

| 有效占比 | 得分 |
|---|---|
| ≥ 60% | 25 |
| 50–60% | 20 |
| 40–50% | 15 |
| 30–40% | 10 |
| 20–30% | 6 |
| < 20% | 0–3 |

再按以下情况各扣 1–3 分（D4 最低 0 分）：
- 同一张表/同一段话重复出现
- 越界设计成块出现（存储模型、表结构、模块拆分、AI 实现方案），且占比 > 30%

## 三、红旗信号（不计分，必须在报告中标出）

| 信号 | 识别方法 |
|---|---|
| **AI 生成的伪 PRD** | 带版本号和修订说明、表格密集、每个字段都有类型和必填规则、自称"已消除冲突/统一口径"，但痛点章节占比 < 15% 或内部有矛盾 |
| **写方案不写需求** | 大量"系统应该…""新增 X 模块"，缺少"因为…" |
| **夹带多个需求** | 一份文档里有多个互不依赖的诉求，应拆开评估排期 |
| **"参考竞品 X"** | 只说参考，没说参考哪一点、为什么 |
| **数字来源不明** | 出现"减负 60%""提升 30%"等数字，没有出处或自称是预估 |

## 四、内容分类定义

| 类别 | 包含 | 不包含 |
|---|---|---|
| 痛点/背景/现状 | 现状描述、遇到的问题、数据、损失、业务类型差异 | 公司介绍、行业大背景、与本需求无关的历史 |
| 用户场景/案例 | 具体角色、具体事件、真实对话/记录示例 | — |
| **业务规则与口径** | 判定标准（什么算有效跟进、什么算合格客户）、阈值（超过 N 天提醒、金额超过多少要审批）、分级条件、枚举值的业务含义（拒绝原因有哪些）、指标口径（分子分母、去重、归因规则）、验收标准、合规边界 | 字段类型、必填校验的实现方式 |
| 业务期望方案 | "希望加个 X""希望能自动 Y"、流程草图 | — |
| **越界设计** | 存储模型、表结构、统一表/分表、**字段定义表**（带"字段类型/必填"列的表格，即使里面列了枚举值也算越界）、多版本数据怎么存之类的数据设计、模块拆分、AI 提取流程与异常处理、技术选型、详细交互 | — |
| 铺垫/重复/套话 | 修订说明、设计原则复述、重复的表格、"综上所述"类总结、文档信息表 | — |

拿不准的段落：问"这条如果业务不写，产品能自己定吗？"——定不了 → 业务规则；定得了 → 越界设计。

字段定义表里确实有业务口径（比如拒绝原因有哪几种）时：整张表仍算越界，但在报告"一页摘要 → 业务给的规则/口径"里把这些枚举摘出来，产品照样能用。

**核心内容占比**（痛点 + 场景）脚本会单独打印。低于 15% 时，即使总有效占比尚可，D1 最高给 20 分，并在红旗里提示"重心在设计而不在问题"。
